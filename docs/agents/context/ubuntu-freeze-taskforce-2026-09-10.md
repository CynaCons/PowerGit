# Ubuntu freeze taskforce — 2026-09-10

Scope: docs/ubuntu-freeze.md + docs/agents/memories/diagnostics.md re-read against the vendored crate sources pinned in frontend/src-tauri/Cargo.lock (tauri 2.11.5, tauri-runtime-wry 2.11.4, wry 0.55.1, tao 0.35.3, tauri-macros 2.6.3, tauri-plugin-dialog 2.7.2/rfd 0.16.0), GTK 3.24 and WebKitGTK 2.44/2.48 sources, and one reproduction attempt. No repo file was edited.

## 1. What the evidence proves now

**The case file's central conclusion is wrong.** §2 "the UI process's main loop is [stuck]" and §7 "The UI process's GTK main loop is what stops" are contradicted by the two snapshots the same section relies on. Every link is in code:

- `heartbeat`, `log_frontend`, `diagnostic_snapshot` (lib.rs:163-293) are bare `#[tauri::command] fn` → tauri-macros wrapper.rs:31/50/266 `ExecutionContext::Blocking`, kind "sync", `body_blocking`: the Rust body runs **inline inside the WebKitGTK callback that delivered the IPC**, no runtime hop.
- On Linux both IPC transports are GLib callbacks of the UI process: the `ipc://` URI-scheme handler (wry web_context.rs:144-262, `webkit_web_context_register_uri_scheme`) and `script-message-received` (wry webkitgtk/mod.rs:630-655). WebKitGTK dispatches both on `g_main_context_default()`, iterated only by tao's `run_return` on the main thread (event_loop.rs:1040-1154, `gtk::main_iteration_do`).
- Therefore "last heartbeat 0.3 s / 0.4 s" means the main loop dispatched a WebKit IPC callback within 0.4 s of the press, and 3 + 4 snapshot presses mean it did so repeatedly and each time ran `write_snapshot` (lib.rs:357-506) on the main thread: `logger.sync`, up to 3 s blocking `tinyhttp::get` per engine JSON, zip, `fs::write`. The "engine idle at 6 req/min" fact was itself fetched by the main thread during the freeze.
- "Only Open repository works" is the strongest evidence of all: tauri-plugin-dialog desktop.rs:148-222 runs rfd inside `run_on_main_thread`, which from a non-main thread is crossbeam send + `MainContext::wakeup`, drained **only** by tao's loop (tauri-runtime-wry lib.rs:235-255, 3335). The picker appearing = tao's loop cycled AND a fresh GTK toplevel painted on the same GdkDisplay/XWayland connection.
- Two refutation passes tried to break this chain and could not (refuted=false, both).

**What the evidence does not prove:** anything about GDK's frame clock, GTK `draw` on the main toplevel, X11 frame sync, or WebKit's UI-side backing store. Nothing the shell measures touches the paint path; that — not a parked loop — is why "no in-app surface can diagnose it". The correct statement: *the default GLib context and tao's main thread were cycling; what is dead is presentation of the main window's WebKitWebView.*

Other corrections, bluntly:

- The inspector argument (§2, §7, diagnostics.md "The freeze is in the UI process") is a non sequitur resting on an event the file elsewhere says never happened: diagnostics.md:120-126 says the inspector never opened on the owner's machine (v0.15.2 and v0.15.3), and `is_devtools_open` is an AtomicBool wry sets unconditionally in `open_devtools` (wry mod.rs:742-760), so "developer tools open=true" proves nothing. If "developer panels" meant the APP LOG tab, the sentence says only "the page does not repaint". Even a real docked inspector shares the toplevel's GdkFrameClock; it freezing does not implicate the loop.
- §2 "Not the Diagnostic snapshot button": the button worked every time and produced the only hard data. Only its on-screen result dialog failed. Same for §4 v0.15.3 "the app log is useless": its data reaches frontend.log via `log_frontend` (works during the freeze); only the rendering is dead.
- §3 "web-process crash ruled out, crash_hooks never fired": crash_hooks.rs shipped in v0.14.2; the v0.14.1 capture had no hook. Valid for the second capture only.
- diagnostics.md §Triggers: the `paint` stall "is the owner's Linux freeze" — it is not; rAF kept firing (2.4 s) in both captures, so the 20 s paint stall never tripped and by construction cannot see this freeze.
- v0.15.0's `WEBKIT_DISABLE_COMPOSITING_MODE=1` was a no-op on top of v0.14.2's switch: since WebKitGTK 2.43.2 the DMA-BUF renderer is the only accelerated backing store, so `WEBKIT_DISABLE_DMABUF_RENDERER=1` alone forces non-AC mode (AcceleratedBackingStore::create returns null; https://raw.githubusercontent.com/WebKit/WebKit/webkitgtk-2.48.0/Source/WebKit/gtk/NEWS). Ubuntu 24.04 is on 2.48.x (https://launchpad.net/ubuntu/+source/webkit2gtk). Every freeze from v0.14.3 on happened with **no GL in the UI process at all**, which is why GL/NVIDIA/DMA-BUF hypotheses rank low.
- The rAF number was over-read. In non-AC mode `DrawingAreaProxyCoordinatedGraphics::update()` sends `DisplayDidRefresh` immediately after `incorporateUpdate` — before GTK paints — so the web process keeps rendering and rAF keeps firing whether or not pixels reach the screen (https://raw.githubusercontent.com/WebKit/WebKit/webkitgtk-2.44.0/Source/WebKit/UIProcess/CoordinatedGraphics/DrawingAreaProxyCoordinatedGraphics.cpp). frameAgeMs is blind to this freeze by design.
- §5/§7 "the main thread's wchan is the answer": given the above, a healthy `poll_schedule_timeout`/`ep_poll` is the **expected** result and settles nothing; freeze-dump.sh captures none of the presentation-side state (no xprop, no journal, no WebKitGTK/mutter versions, no GPU line, no `/proc/pid/environ`).
- §7 "never reproduced": the container harness runs Xvfb/weston-headless with no mutter, no occlusion, no idle, no GPU. Its result is not evidence for or against any presentation hypothesis and should not have motivated compositing-off.
- §4 v0.15.4: the flush-under-mutex defect is a genuine parked-loop mechanism, but only for v0.15.2-v0.15.3 focus freezes; the captured freezes predate it and the v0.15.5 report postdates the fix. Keep the fix; stop treating it as the mechanism.
- Scope caveat, kept honest: "loop alive" is **proven** for the two captures (v0.14.1, v0.14.3) and **inferred** for v0.15.1-v0.15.5 (same shape, no capture).

## 2. Ranked hypotheses

**H1 (high) — GTK3 X11 frame-sync stall under XWayland: the toplevel's GdkFrameClock is frozen waiting for a `_NET_WM_FRAME_DRAWN` mutter never sends.**
Mechanism: `gdk_x11_window_end_frame` sets `frame_pending = TRUE` and `_gdk_frame_clock_freeze()` after every frame whenever the WM advertises `_NET_WM_FRAME_DRAWN` (https://gitlab.gnome.org/GNOME/gtk/-/raw/gtk-3-24/gdk/x11/gdkwindow-x11.c); the clock thaws only on that ClientMessage or on UnmapNotify, with no timeout (https://gitlab.gnome.org/GNOME/gtk/-/raw/gtk-3-24/gdk/x11/gdkdisplay-x11.c). A frozen clock skips every paint phase while all other GSources (IPC, timers, input, other toplevels' clocks) keep dispatching. Mutter drops that message for XWayland actors it does not paint — off-workspace, occluded, minimised, other monitor, mixed refresh/VRR: https://gitlab.gnome.org/GNOME/mutter/-/issues/1577, https://gitlab.gnome.org/GNOME/mutter/-/issues/2772, https://github.com/prusa3d/PrusaSlicer/issues/15007, and the near-twin **Tauri** case https://github.com/anomalyco/opencode/issues/11939 (GNOME/NVIDIA, forced GDK_BACKEND=x11, same WEBKIT_* switches, Rust and UI heartbeats alive, gnome-shell logs "Frame has assigned frame counter but no frame drawn time", fixed by native Wayland). The forced x11 comes from tauri-bundler's GTK hook: https://github.com/tauri-apps/tauri/issues/15781.
Fit: every symptom. Loop alive; picker paints (own toplevel, own clock, own sync counter); window moves/resizes (mutter does that) but exposed regions stay black (GTK never paints them); docked inspector shares the clock; "background then come back" and "loses focus" are exactly when mutter stops painting the actor; WEBKIT_* switches irrelevant (they change what WebKit hands to `draw`, not whether `draw` runs); rAF keeps firing (non-AC, above); container harness cannot show it.
Discriminating test: **`POWERGIT_WAYLAND=1` for a week of normal use.** The Wayland backend uses wl_surface frame callbacks; the frozen code path does not run. Corroboration on the next freeze: `journalctl --user -b | grep -i 'frame drawn'` and a shell-side after-paint counter that stops while heartbeats continue.

**H2 (medium) — mutter/XWayland stops presenting the window's buffers although GTK paints** (unredirected XWayland windows not updated, windows hidden after screen reconfiguration https://gitlab.gnome.org/GNOME/mutter/-/issues/4133, NVIDIA stale-frame presentation https://github.com/NVIDIA/open-gpu-kernel-modules/issues/187).
Fit: same trigger set, same invisibility to the shell; fits black exposed regions less well.
Discriminating test: the after-paint/`draw` counter **keeps advancing** while the screen is dead (H1: it stops). Same mitigation: leave XWayland.

**H3 (low) — WebKit UI-side GL/DMA-BUF fault (NVIDIA import, EGL after suspend)** (https://bugs.webkit.org/show_bug.cgi?id=261874, https://v2.tauri.app/develop/debug/linux-graphics/).
Fit: excluded as root cause for v0.14.3+ (non-AC, no UI-process GL); could only explain the v0.14.1 capture, which had the identical shape. Test: `POWERGIT_KEEP_DMABUF=1 POWERGIT_KEEP_COMPOSITING=1` — in AC mode `FrameDone` is only sent from the GTK draw handler, so a frozen clock would stop rAF and trip the paint watchdog; a shape change there is informative for H1.

**H4 (very low) — parked main loop (the case file's conclusion).** Refuted by §1 for the captures. Residual: the rfd `GtkGlobalThread` (rfd gtk3/utils.rs) spawns, on the first native dialog, a thread that iterates the **default** context forever, contending with tao's thread; after a dialog, GTK/WebKit callbacks can dispatch on that thread. Not a parked loop, but an unverified thread-affinity hazard for GDK/EGL state; test by logging `gettid()` in the paint counter and whether a dialog preceded the freeze.

**H5 (very low) — page/WebKit "hidden" state never resumed.** frontend.log visibility lines and non-null frameAgeMs already argue against it; check the last visibilitychange before a freeze is `visible` and stop.

Prediction for the owner's next freeze-dump: main thread in `do_sys_poll`/`ep_poll`, engine 200 — the "healthy" row. Do not read that as "settled".

## 3. Change list for the next release, in priority order

1. **Default to native Wayland when `WAYLAND_DISPLAY` is set; keep x11 as opt-in** (`POWERGIT_X11=1`). Files: frontend/src-tauri/src/main.rs (env handling), AppImage hook override, docs. Accept: on a GNOME Wayland session `shell.txt` shows `GDK_BACKEND=wayland`, the frameless title bar drags/resizes, and the freeze does not recur in a week of owner use. Risk: WebKitGTK Wayland glitches https://github.com/tauri-apps/tauri/issues/12361; hence the opt-out. Ship behind the env var first if the drag test fails.
2. **`POWERGIT_NO_FRAME_SYNC=1`** — after realize, `gtk_window.window().downcast_ref::<gdkx11::X11Window>().set_frame_sync_enabled(false)` (gdkx11-0.18.2 x11_window.rs:58; public GDK3 API, https://docs.gtk.org/gdk3-x11/method.X11Window.set_frame_sync_enabled.html). Files: Cargo.toml (linux deps `gtk = "0.18"`, `gdkx11 = "0.18"`, both already in Cargo.lock), lib.rs setup inside `run_on_main_thread`. Accept: engine.log logs "frame sync disabled (X11)" or "not an X11 window"; the X11 fallback experiment for owners who must stay on x11.
3. **Paint probe that works with a live loop** — new frontend/src-tauri/src/probe.rs: atomics for GdkFrameClock `after-paint` (count, last-at, `frame_counter()`), toplevel `connect_draw`, WebKitWebView `connect_draw` (via `with_webview`), `mapped`, plus a 1 px `queue_draw_area` stimulus every 2 s from the shell and a 1x1 opacity toggle per beat in useHeartbeat.ts (opt-out `POWERGIT_PROBE_PAINT=0`). Reconnect the clock on `map` (realize can hand out a new clock); never `add_tick_callback`. Also log `gettid()` of the draw handler vs the tao thread (H4 residual). Accept: shell.txt gains `gdk after-paint: N, last X s ago (requested Y s ago)`, `toplevel draw`, `webview draw`, `window mapped`; in the container harness all ages stay < 3 s.
4. **Liveness round-trip + `probe.txt`** — a `powergit-liveness` std thread sends a `run_on_main_thread` closure and a `glib::idle_add_full(Priority::DEFAULT, ..)` every 2 s, records rtt/pending; rewrites `<log dir>/probe.txt` atomically every 10 s and on threshold; logs `probe: loop tauri 0.3ms glib 0.2ms | gdk paint 0.9s (req 0.1s) | webview draw 1.1s | beat 0.3s | frame 0.2s` every 30 s (5 s when stale). Never `MainContext::invoke` (runs on the caller when the context has no owner, glib main_context.rs:35-44). Files: probe.rs, lib.rs, snapshot zip. Accept: `probe.txt` exists and is < 15 s old while the app runs; the four outcomes (A loop ok/gdk frozen, B gdk paints/webview not, C all paint/screen dead, D loop stalled) are readable from it.
5. **Watchdog kinds** — `Observation.gdk_paint_age`, `loop_age`; `Stall::Presentation` (beats + page frames but no GTK paint for 20 s while mapped) and `Stall::Loop` (no round-trip for 15 s; snapshot + incident only, never Reload/AskRestart, outranks all). Files: watchdog.rs (+ tests), lib.rs, frontend/src/diagnostics/snapshot.ts (`describeIncident` for "presentation"/"loop"). Accept: new pure tests pass; existing tests unchanged (fields default None).
6. **Recovery ladder the owner can drive** — `recover(step)` sync command that only enqueues main-thread closures (never a tauri getter off-thread); steps `1 queue_draw`, `2 thaw`, `3 hide_show`, `4 resize`, `5 present`, `6 frame_sync_off+hide_show`, `7 reload`, `8 new_window` (label `recovery-*`, needs capabilities/default.json), `9 webview_snapshot` (`webkit_web_view_get_snapshot`, 5 s timeout); each logs `recover #N <key>: requested/done` and a +3 s probe readout. Triggers: Ctrl+Shift+F1..F9 in frontend/src/hotkeys/Host.tsx capture phase (IPC is proven alive), `<log dir>/recover.request` polled by the liveness thread (`scripts/freeze-dump.sh recover <key>`), Settings → Tools list. Accept: on a healthy Linux build each step logs done < 1 s and the probe ages reset; expected under H1: only 3/6/8 restore the picture (`queue_draw`/resize cannot thaw a frozen clock; `WebviewWindow::reload` cannot either).

```

Send the freeze tarball, the snapshot zip, and the list of what recovered.

Preventive run for the next week, one variable at a time, a day each: `POWERGIT_WAYLAND=1 ./PowerGit_*.AppImage` first; if a freeze still occurs, `POWERGIT_NO_FRAME_SYNC=1` (after item 2).
