# Performance audit — 2026-09-23 (v0.20.5): the graph on Windows and on Linux

Owner (2026-09-23): "would you run for me a performance audit on the app? Just
to be sure that our graph engine is really super smooth, also on linux."

This iteration (v0.20.6) measured and fixed nothing. It re-measured the graph
on the **production build** after the v0.18.13 – v0.18.18 fixes of the
[2026-09-16 audit](audit-2026-09-16.md), and measured **Linux (WebKitGTK)**
for the first time, with a probe that runs inside the real webview.

## One page for the owner

**On Windows the graph is smooth.** Every everyday interaction holds 60 fps
or answers inside a frame, on repositories up to 165k commits.

**One interaction is not smooth anywhere: dragging the scrollbar** (or any
jump of a screen or more). Each frame mounts a fresh screen of rows and spends
26 – 40 ms restyling them, so a drag runs at 15 – 25 fps in Chromium. The
earlier audit never jumped, so this is new, and it is the graph's one real
item.

**On Linux we cannot yet say "smooth", and the reason is ours to decide.**
The shell switches WebKitGTK's GPU path off for every Linux user
(`main.rs`: `WEBKIT_DISABLE_DMABUF_RENDERER=1`,
`WEBKIT_DISABLE_COMPOSITING_MODE=1`, the v0.14.2 / v0.15.0 freeze
workarounds), so WebKitGTK paints in software. In WSL that gives ~12 fps
scrolling — but a plain HTML list with no React and no canvas scrolls at the
same ~12 fps in the same window, so the graph adds nothing on top of the
webview; the webview is the ceiling. WSLg's own GPU path does not work in
this VM, so it cannot tell us what a real Ubuntu desktop does with the
switches on or off. **That needs one probe run on the owner's Ubuntu machine**
(§6).

The fairest single comparison: the same probe, the same repository, the same
dpr 2 — **the real Windows app (WebView2) scrolls the graph at 60 fps with no
janky frame; the real Linux app (WebKitGTK in WSLg) at ~12 fps, which is also
what a plain HTML list gets there.**

| what the user feels | Windows, production (Chromium / WebView2) | Linux, WSLg WebKitGTK (shipped switches) | 2026-09-16 (Windows, dev build) |
|---|---|---|---|
| continuous scroll (trackpad-like, 24 px/frame) | 60 fps, 0 janky frames (WebView2 at dpr 2 too) | 12 fps (plain-list control: 12 fps) | not measured |
| wheel scroll (400 px / 50 ms, 6 s) | 60 fps; 0 long tasks; 1 frame > 32 ms | 15 fps (control-bound) | 0 long tasks, 39 – 58 frames > 32 ms |
| scrollbar drag (skim, 60 frames top → bottom) | **p50 50 ms, p95 117 ms per frame**; 26 long tasks / 2.0 s | p95 120 – 147 ms | not measured |
| hover → graph redraw | 12 – 14 ms (audit), 0.8 ms p50 (probe) | 2 ms p50 | 32 – 34 ms |
| click → row highlighted | 19 – 23 ms | 29 – 42 ms | 62 – 65 ms |
| click → Commit tab | 102 – 175 ms (git-bound) | 118 – 181 ms | 140 – 221 ms |
| ancestry on / exit | 23 – 31 / 55 – 71 ms | not measured | 87 – 94 / 110 – 159 ms |

## 1. Method

- Machine: i7-1185G7 (4 cores / 8 threads), 16 GB, Windows 11 26200, git
  2.38.1 (Windows) / 2.43.0 (WSL). WSL2 Ubuntu 24.04.3 with WSLg (Weston over
  RDP, display scale 180 – 200 %, so the Linux page runs at dpr 2),
  WebKitGTK 2.52.6.
- Build: **production** (`vite build`), not the dev server. Engine: Release
  (`dotnet publish -c Release`; linux-x64 self-contained single file,
  cross-published from Windows, for WSL). Each side has its own engine,
  token, `POWERGIT_DATA_DIR` and ports (Windows :7761 / UI :1461 – 1462, WSL
  :7762 / :1462) — nothing touched the owner's recents or :7733.
- Windows, Chromium: `scripts/perf-audit.mjs` (Playwright + CDP, unchanged
  method from 09-16) against `vite preview`; 3 runs PowerGit, 2 runs flutter
  and vscode. New this time: a `skim` scenario, and profile rows carry the
  column (a minified bundle is one line).
- Both webviews: `src/perf/probe.ts`, an in-app probe compiled in only when
  `VITE_PERF_PROBE` is set (a normal build has no probe chunk; checked). It
  runs the scenarios from inside the page — rAF frame deltas, graph-canvas
  redraws via `clearRect`, DOM waits — and posts JSON to
  `scripts/perf/probe-sink.mjs`. `scripts/perf/probe-report.mjs` prints the
  tables. The shell (Tauri, debug profile; rendering is the webview's, not
  Rust's) was built with `TAURI_CONFIG` pointing its window at the probe
  bundle, 1600×1000.
- Probe scenarios: `control24` (a plain 3,000-row HTML list, no React, no
  canvas, scrolled 24 px per frame — the webview's own ceiling), `fling24` /
  `fling96` (the grid, 24 / 96 px per frame for 5 s), `jump` (the audit's
  400 px / 50 ms), `skim` (top to bottom of the loaded rows in 60 frames),
  `hover` (40 rows), `select` (20 SHA-cell clicks). "Janky" = a frame longer
  than 1.5 × the display interval (floored at 16.7 ms, because WSLg's rAF is
  not display-synced and idles at ~9 ms).
- Validation: the probe in headless Chromium reproduces the audit script's
  numbers (60 fps scrolls, highlight 19 – 21 ms, Commit tab 114 – 169 ms).
- Test beds as on 09-16: PowerGit (17.9k commits, 293 refs, nested
  submodules), flutter (97k commits, 2,146 refs), vscode (165k commits,
  5,577 refs). In WSL each was recreated on ext4 from a copy of its `.git`
  with a fresh checkout, so refs are identical and no CRLF noise reaches
  `status`.

## 3. Linux (WebKitGTK 2.52.6 under WSLg), the real shell

2 runs each, medians. dpr 2 (WSLg's scale; `GDK_SCALE=1` did not change it).

| configuration | control fps / p95 | grid fling24 fps / p95 | jump fps | skim p95 | hover p50 | highlight / Commit tab |
|---|---|---|---|---|---|---|
| **shipped** (Wayland, DMA-BUF off, compositing off), PowerGit | 11.8 / 99 ms | 12.4 / 103 ms | 15.2 | 120 ms | 2 ms | 39 / 138 ms |
| shipped, X11 (`POWERGIT_X11=1`) | 10.9 / 122 ms | 10.6 / 125 ms | 12.4 | 142 ms | 2 ms | 39 / 161 ms |
| compositing kept (`POWERGIT_KEEP_COMPOSITING=1`) | 11.7 / 98 ms | 12.3 / 103 ms | 16.9 | 119 ms | 2 ms | 39 / 152 ms |
| GPU path (`…KEEP_COMPOSITING=1 …KEEP_DMABUF=1`) | 6.8 / 321 ms | 3.7 / 425 ms | 3.2 | 301 ms | — | 39 / 164 ms |
| shipped, flutter | 11.7 / 115 ms | 11.7 / 110 ms | 12.2 | 142 ms | 2 ms | 29 / 118 ms |
| shipped, vscode | 12.5 / 99 ms | 11.8 / 113 ms | 15.4 | 136 ms | 2 ms | 42 / 181 ms |

Boot on Linux: first row / settled 1.6 / 2.5 s (PowerGit), 3.7 / 8.6 s
(flutter), 4.4 / 11.9 s (vscode).

Reading it:

- **The grid scrolls exactly as fast as a plain list** in every
  configuration (fling24 vs control within 1 fps). On this webview the app
  is not the limit.
- **The limit is software painting at dpr 2.** The shipped switches force
  WebKitGTK's non-accelerated backing store (since 2.43.2 the DMA-BUF switch
  alone does that, `main.rs` says so), and WSLg adds a 180 – 200 % scale.
- **The GPU path is worse here, not better** — WebKitGTK logs
  `MESA: error: ZINK: failed to choose pdev` / `egl: failed to create dri2
  screen`: WSLg's d3d12 GPU is not reachable from WebKitGTK's EGL in this VM.
  So WSL cannot answer whether the switches cost a real Ubuntu desktop its
  60 fps.
- Hover (2 ms) and selection (29 – 42 ms highlight) are fine on Linux:
  they redraw little.

## 4. Findings, ranked by what the user feels

1. **Linux paints the graph in software, for everyone** — `src-tauri/src/main.rs`
   sets `WEBKIT_DISABLE_DMABUF_RENDERER=1` and `WEBKIT_DISABLE_COMPOSITING_MODE=1`
   unless `POWERGIT_KEEP_DMABUF` / `POWERGIT_KEEP_COMPOSITING` is set. They
   were the first freeze workarounds (v0.14.2, v0.15.0); the 2026-09-10
   taskforce later placed the freeze in GTK's X11 frame sync and v0.15.6 moved
   Linux to native Wayland — whose owner tick is still open. On a real GPU the
   switches may cost smoothness, especially on HiDPI screens; they may also
   still be what keeps some driver/compositor pair from going black. Only a
   run on real hardware can weigh that (§6). **Not changed in this audit.**
2. **Scrollbar drag / big jumps restyle a fresh screen of rows every frame:
   26 – 40 ms of style recalc per frame in Chromium** (CDP: `RecalcStyle`
   2.5 s of a 3.2 s skim, script 0.29 s, layout 0.18 s). Cleared: selectors
   (Chrome selector stats: 8 ms of matching in 441 ms of recalc), custom
   properties (86 on `:root`, none set per row), JavaScript. ~36 µs per
   element over ~400 elements per frame. The shape of the fix is to stop
   mounting new elements on a jump — virtual rows keyed by slot, not by SHA,
   so a jump rewrites text in place — measured with `skim` (budget: p95 ≤
   33 ms in Chromium). The real WebView2 app shows the same p95 200 ms.
   Every platform feels this; Linux feels it most.
3. **`git submodule status --recursive` on every refs refresh: 0.8 – 0.9 s**
   on Windows in any repository with submodules (PowerGit has two, nested).
   It is the largest single git call of PowerGit's boot (919 ms) and F5
   (792 ms). `GitHost.Queries.cs:1112`; `git submodule status` spawns
   `describe` per module. A cheaper source (`ls-files --stage` for mode
   160000 + the submodule's `HEAD`) or caching it until `.gitmodules` or a
   gitlink changes.
4. **A ref filter over thousands of refs leaves the graph blank for ~5.6 s**
   (vscode, 5,210 or 5,577 refs). Not a regression: the request is a body since
   v0.18.14 and the rows come back; `git log` with 5,577 tips on stdin costs
   4.7 s for the first 1,000 rows (5 tips: 1.4 s). The audit's own
   `rowsStable` gave up after 5 quiet seconds and called the grid empty — a
   harness artifact; the filter scenario now waits for the rows to come back
   before it waits for the grid to settle (`scenarios.mjs`). A
   spinner or keeping the previous rows until the new ones arrive would make
   the wait legible.
5. **Boot on the biggest repository is git-bound**: vscode 2.4 s to the
   first row on Windows, 4.4 s on Linux (4 × `log --date-order` pages =
   5.4 s of git). Acceptable; listed because it is the one boot number above
   2 s.

## 5. Not measured, and why

- **Real Ubuntu hardware.** WSLg's GPU path is broken for WebKitGTK here and
  its display scale is fixed at 180 – 200 %; see §6.
- **Linux at dpr 1.** `GDK_SCALE=1` does not override WSLg's scale.
- **Pending-changes scenarios.** The owner asked about the graph; the
  pending lists were fixed in v0.18.13 and have their own budgets in
  `tests/perf/pending.spec.ts`.
- **macOS.** Not a target.

## 6. The one run that would settle Linux

On the owner's Ubuntu machine, the probe build of the shell against the
three repositories, twice: with the shipped switches, and with
`POWERGIT_KEEP_DMABUF=1 POWERGIT_KEEP_COMPOSITING=1`. If the GPU path holds
60 fps there and does not freeze, the switches can become opt-in; if it
freezes, they stay and item 2 matters twice as much on Linux.

## 7. Reproduce

Windows (Chromium, CDP) — Release engine on :7761, production UI on :1461:

```powershell
# engine: dotnet publish -c Release; run with POWERGIT_ENGINE_TOKEN, POWERGIT_DATA_DIR,
# POWERGIT_ENGINE_ORIGINS=http://127.0.0.1:1461,http://127.0.0.1:1462 --urls http://127.0.0.1:7761
cd frontend
$env:VITE_ENGINE_URL='http://127.0.0.1:7761'; $env:VITE_ENGINE_TOKEN=(Get-Content .engine-token -Raw).Trim()
npx vite build --outDir <dir> --sourcemap; npx vite preview --port 1461 --outDir <dir>
$env:PW_PORT='1461'; $env:POWERGIT_ENGINE_URL='http://127.0.0.1:7761'
node scripts/perf-audit.mjs --repo C:\dev\perf\vscode --runs 2 --label win-prod-vscode
```

Probe (any webview): build with `VITE_PERF_PROBE=http://127.0.0.1:<sink port>`
plus the engine URL and token, serve it, build the shell with
`TAURI_CONFIG='{"build":{"devUrl":"http://127.0.0.1:1462"}}'`, start
`node scripts/perf/probe-sink.mjs --port <sink port> --label <label> --repo-id <id> --runs 2`,
launch the shell; the sink writes the JSON and exits.
`node scripts/perf/probe-report.mjs <json…>` prints the table. WSL's
localhost relay forwards WSL ports to Windows: stop the WSL static server
before a Windows probe run on the same port, or the Windows page loads the
Linux bundle.
