# Performance audit — 2026-09-16 (v0.18.10)

Owner (2026-09-16): "We need to have a go at performance. We need to evaluate
the performance of the UI when the user is interacting with the graph. Also
I've had cases where when there's a lot of pending changes, the app becomes
unusable."

This iteration measured and fixed nothing. The numbers below come from
`frontend/scripts/perf-audit.mjs` (Playwright + CDP driving the real UI
against a private harness engine; see
`docs/agents/memories/perf-audit-harness.md`) on three real repositories and
three generated working trees. Every table says which build and how many runs;
the per-run values are in `frontend/test-results/perf/*.json` (not committed).

## 1. Method

- Machine: 11th Gen Intel Core i7-1185G7 (4 cores, 8 threads), 16 GB, Windows 11 Home 26200, git 2.38.1.windows.1, node 22.16, .NET 10 engine built by `dotnet run` (Debug).
- Build: **Vite dev server** (`npx vite --port 1461`), headless Chromium (Playwright 1.55), viewport 1600×1000. The dev build carries React's development instrumentation: `selection-pipeline.md` measured production 3 – 5× faster on render and identical on the network. Every render number here therefore *ranks* bottlenecks; the production run (§8) was not done in the time box. Engine numbers (git durations) are build-independent.
- Harness engine: `frontend/scripts/e2e-harness.ps1 -Name perf -UiPort 1461 -EnginePort 7761` — own token, own `POWERGIT_DATA_DIR`; nothing reached the owner's recents. The default engine (:7733) was never pointed at an audit repository.
- Recorded per scenario (all in-page unless said): long tasks (`PerformanceObserver` longtask: count, total, max), rAF frame deltas (> 32 ms count, max), graph-canvas redraws (a wrapper on `clearRect` for `.graph-canvas`: `draw.ts drawRows` clears first, so one clearRect is one redraw), input timestamps (capture-phase listeners), CDP `Performance.getMetrics` deltas (script / layout / style time, DOM nodes, heap), heap after a forced GC, the sampling profiler's top self-time functions (scroll, hover), and the engine's git command log (`/gitlog`, polled every 250 ms) cut to the scenario's wall-clock window.
- Runs: 3 for PowerGit and the pending trees at 500 and 2,000; 2 for flutter, vscode and the PowerGit re-run of the corrected scenarios; 1 for pending-10,000 (each run took minutes and the third measurement changes no conclusion). Tables show medians; the run-to-run spread is quoted where it matters.
- Test beds: PowerGit worktree (17.6k commits, 289 refs); C:\dev\flutter (97,295 commits, 2,146 refs, branch `beta`, read-only); C:\dev\perf\vscode (165,365 commits, 5,577 refs, 18,930 tracked files); `scripts/perf/make-pending.mjs` trees with N = 500 / 2,000 / 10,000 modified files, N/4 untracked, N/10 staged (675 / 2,700 / 13,500 status lines). The Linux kernel was not cloned: vscode already shows the engine ceilings (§4) and the pending trees the UI ceilings.

## 4. Bottlenecks, ranked by what the user feels

1. **The pending file lists render every file as an MUI `Box`, three per row, no virtualizer** — `components/CompactFileList.tsx` (used by `CommitFileLists.tsx` for the commit window's two lists and by `DiffTab.tsx` for the Diff tab). Evidence: DOM nodes +68,070 and 30.4 s of script for the commit window at 12,500 files; +14,066 and 2.4 s at 2,500; a single 6.6 s long task; heap 915 MB. The scaling is linear in N and the constant is ~2.3 ms per row in dev (≈ 0.5 – 0.8 ms in production, so 12,500 files would still be 6 – 10 s). This is the owner's "unusable" case.
2. **Every status answer is a new object and re-renders every pending row, twice** — `hooks/useRepoState.ts` `client.status().then(setStatus)` has no equality check (`historyMerge.ts` gives revisions one; status has none). Downstream: `BottomPanel.tsx:115 pendingOf(current, status)` builds a new `files` array → `DiffTab`'s list re-renders every row and `pendingRows.ts usePendingDiff` re-fetches the worktree diff (`ls-files --error-unmatch` + `diff --no-color` per refresh: 8 pairs for 4 refreshes in the N = 500 storm); `CommitDialog` re-renders both lists. The 10 s `STATUS_POLL_MS` and every SSE-driven refresh therefore cost the full list render: 3.5 s per poll at 2,500 files, measured as 107 s of long tasks in a 300 s window with the window open. Staging one file pays it twice (the stage answer sets status, then the echo-guarded refresh sets it again): 5.5 s at 2,500 files.
3. **Stage all cannot stage 2,500 files on Windows** — `GitHost.Queries.cs Stage()` builds `git add -- <every path>`; 2,500 paths × ~20 chars > 32,767. The command log shows `add --` with 0 ms and no `add` ever ran; the lists stay as they were. Reported as a defect, not a perf item, but it is what the owner meets right after the slow window. (`git add --pathspec-from-file=-` on stdin, or `git add -A`/`-u` for "all", is the shape; the same applies to `restore --staged` for unstage-all and to every `paths` route: `files/delete`, `files/reset`, `patch`, `ignore`.)
4. **Ref filter with more than ~250 refs answers 414 and the grid goes blank** — `useHistory.fetchPage` sends `GET /revisions?ref=<full name>&…`; 289 refs = 8,898 characters > Kestrel's 8 KB request line. The engine side already streams the names on stdin (graph-ref-filter.md) but the transport to the engine is the URL. On vscode a single tick on a remote folder (5,210 refs) does it. The `TypeError: Failed to fetch` is an unhandled rejection (`[powergit] unhandledrejection` in the console), so the user sees an empty graph and nothing else.
5. **`for-each-ref … %(refname:short)` is 95 % of `/refs`** — 2,578 ms of 2,700 on vscode, ~1.1 s on flutter, on every F5, every refs-scoped refresh, every boot. Deriving the short name in C# (strip `refs/heads/`, `refs/remotes/`, `refs/tags/`, keep `refs/…` for anything else) makes it 130 ms.
6. **History pages cost 1 – 1.5 s each on a repository with thousands of tips, independent of `skip`** — `ListRevisions` runs a fresh `git log --date-order --decorate=short --branches --remotes --tags -n 1000 --skip N` per page; boot's eager 10 pages are 10 – 15 s of git on flutter / vscode (settle 11.7 s / 17.0 s), and the page appends are the only long tasks during boot (28 – 29 × ~75 ms, max 269 ms in dev). Larger pages (2,000 – 5,000) or one long-lived streaming log would remove the per-page setup; `--skip` itself is cheap here.
7. **`graphWidth(rows)` walks all 10,000 rows on every RevisionGrid render** — `draw.ts:56`, called unmemoised in `RevisionGrid.tsx` (`const naturalWidth = graphWidth(rows)`); each scroll frame and each hover re-renders the grid, so it is 143 – 216 ms of self time in a 6 s scroll and the largest app-owned function in both profiles. A `useMemo` on `rows`. Small, but it is the one graph item the traces name.
8. **Hover re-renders every visible row** — `RevisionRow` is not `memo`ised; `setHovered` re-renders `RevisionGrid`, its ~45 `RevisionRow`s and their `RefChips` (`orderRefs` + `foldRefs` per row), then the canvas effect redraws the visible bands. Cost today: 32 – 34 ms hover → redraw in dev (≈ 8 – 12 ms production), 1 – 2 long tasks per 40 hovers. It is under a frame in production; listed because the ranking asked for it, not because the user feels it.

## 5. Suspects: confirmed or cleared

| suspect | verdict | evidence |
|---|---|---|
| `GetStatus` runs `status -uall` + `ls-files -v -z` + `rev-parse` ×2 + `rev-list` on every refresh | **Confirmed, but it is not what hurts**: six processes, 300 – 400 ms flat from 675 to 13,500 status lines; `status -uall` itself 82 → 193 ms; `ls-files -v` 36 → 45 ms. On vscode's 18,930-file clean tree `status` is 605 – 739 ms (fs stat bound; `core.fsmonitor` would help there). | §3 status-direct, command log |
| The pending file lists have no virtualizer | **Confirmed, #1.** | §3 diff-tab, commit-window: +63k / +68k DOM nodes, 13 s / 29 s at 12,500 files |
| Live refresh re-runs status on every `.git/index` write; does a storm queue requests? | **Cleared for queuing, confirmed for cost**: the 400 ms debounce + echo guard coalesce 20 index writes in 2 s into 1 – 4 `/status` calls, never more than 1 in flight (`statusMaxInFlight` = 1). Each answer then re-renders the lists (#2). The 200 appended tracked files were invisible to the watcher, as designed; the 10 s poll catches them. | §3 storm |
| Hover → every RevisionRow re-renders; `draw.ts` redraws the whole canvas | **Confirmed but cheap**: 32 – 34 ms in dev, one redraw per hover (`redraws` = 40 for 40 hovers), only the visible bands are drawn. | §2 hover, profile |
| `RefChips` measures text per render | **Cleared**: `refChipsModel.ts textWidthOf` caches per name in a `Map`; `measureText` is not in the profile. `foldRefs`/`orderRefs` do run per row per render (sorts over ≤ 10 names). | code + profile |
| Paging: what ceiling, how many rows does flutter load, memory, does the layout worker keep up | 10,000 rows eager (`EAGER_CEILING`), 100,000 hard; flutter and vscode both stop at 10,000 (heap 40 / 112 MB after GC). The worker keeps up: the only long tasks during the load are the main-thread appends (`[...prev.slice(0, from), ...rows]`, `withArtificialRows`, `markAncestry` over all rows, the virtualizer's key/measure pass) at ~75 ms median, 250 – 280 ms max in dev, 28 – 29 per boot. The engine is the boot's clock (git 14 – 21 s of the 12 – 17 s settle, in parallel with the UI). | §2 boot |
| Anything else the traces show | `graphWidth` (#7) and React's dev-mode JSX runtime are the top app-visible self time; nothing else above 100 ms. | profiles |

## 6. Defects found on the way (blocking the scenarios, described, not fixed)

- Stage all / unstage all above ~1,300 paths on Windows: `git add -- …` cannot spawn (§4 #3). Also seen from the harness: `stage-all` at N = 2,000 showed no error banner during the 300 s watch; whether the dialog reported the spawn failure was not checked.
- Ref filter with > ~250 refs (or any remote folder on a big repository): HTTP 414, empty graph, unhandled rejection (§4 #4). The existing e2e (`graph-branch-filter.spec.ts`) uses 3 refs.
- `npm run test:perf` was broken before this iteration: `perf-run.mjs` starts its Vite on :1421 but the engine only allows :1420 origins (CORS lockdown, v0.13.0), so the UI sat at "connecting to the engine… (attempt 5)" and `heavy.spec` failed on its first test; the `engine-status` contains "(" assertion passed on that very text. The orchestrator now passes `POWERGIT_ENGINE_ORIGINS` for :1421, sets `POWERGIT_DATA_DIR` (its fixtures were landing in the owner's Recent repositories), and forwards extra arguments to Playwright (`node scripts/perf-run.mjs --grep pending`). Harness scripts, not product code. The suite is green again: 7 passed (3 heavy + 4 new).
- The heavy fixture's 2,500 refs were loose files (`update-ref --stdin`): `git show --format=%D` cost 321 ms against 84 ms packed, so the selection latency on that fixture (748 – 1,002 ms) was the fixture, not the app. `make-heavy-repo.mjs` now runs `git pack-refs --all` (stamp v2, regenerates once). Real repositories meet the same thing after fetching thousands of branches until `gc` packs them — a `pack-refs` after fetch is a cheap engine-side idea. Oddity for the record: `for-each-ref … %(refname:short)` on that fixture is 1.0 s loose and 1.4 – 1.6 s packed; the heavy filter test now waits for the tree before timing the filter.
- `expand` could not be measured on PowerGit / flutter at 1600 px: no row folds a chip at that width; vscode has one (93 / 53 ms). The +n path is the same code either way.

## 8. Not measured, and why

- **Production build** (`vite build` + `vite preview`): not run in the 3 h box. Expect render numbers 3 – 5× lower (§1); the ranking does not change because #1 – #6 are linear-in-N renders and engine time.
- **The Linux kernel** (1.3M commits): not cloned; vscode already shows the per-page and per-ref engine ceilings and the eager ceiling of 10,000 rows bounds the UI.
- **Ref filter on flutter**: the harness found no tickable tree row (sections collapsed above the threshold); vscode covered the case, with the 414 outcome.
- **Storm at N = 10,000**: the page was still stalled from "stage one"; the N = 500 / 2,000 storms answer the queuing question.
- **The Chromium trace's Paint events**: the in-page `clearRect` wrapper was enough for "input → canvas"; a `Tracing`-domain paint timeline was not needed.
- **RefChips / RevisionRow render counts** via the React profiler: not wired; the sampling profiler and the CDP script time were the evidence.
