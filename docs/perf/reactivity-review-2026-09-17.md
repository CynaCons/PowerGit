# Reactivity review — 2026-09-17

Owner: "I have a feeling like it's slow, sluggish, lagging. Not very smooth and reactive."

Method: five read-only finders, one dimension each (render cascade from App, grid and canvas, bottom panel and diff, engine latency on the interaction path, paint/compositor/shell), 46 raw findings, 39 distinct after dedup by file and line, the 24 highest-ranked each handed to a skeptic prompted to refute it — 13 confirmed, 11 refuted, 15 never verified. The confirmed list, with the skeptics' reasons, impact estimates and fixes, is the appendix. The plan is iteration v0.18.18.

## The amplifier

`frontend/src/App.tsx:365` passes `onSelect={(i) => setSelectedSha(…)}` inline. `RevisionGrid.tsx:284-299` puts it in the deps of `clickRow` and `contextRow`, which are props of every `RevisionRow`; `memo(RevisionRow)` (v0.18.16) therefore never holds across an App render, and ~60 rows (36 visible + overscan) re-render with their RefChips instead of the two whose selection changed.

App renders: twice per click (urgent and deferred pass), twice every 10 s (the status poll flips `refreshing` true/false even when the status answer is unchanged, `useRepoState.ts:48/73`), twice per action, once per splitter pointermove (`useChromeLayout.ts:50`), every 400 ms during a fetch (the job poll), per frame of the command-rail width transition (`CommandRail.tsx:88`). Five of the thirteen confirmed findings name this as what makes them expensive.

Also: `GitHost.Queries.cs:371` — `RenamedFrom` (v0.18.15) spawns a whole-commit `diff-tree` on every per-file diff, serially before the `show`.

## Ruled out

`GetStatus`'s four git processes every 10 s (measured cheap in the 2026-09-16 audit); `BottomPanel` not being memo'd (its props are identity-stable; the deferred pass is the design); the 3,000-row JSON parse on window focus (real but bounded); `EngineProvider`'s fresh context value (no memo'd consumer on the hot path reads it).

## Not looked at yet

The graph's own interactions (click, hover, keyboard, compass, page append, right-click) and the bottom panel's resize ("jumping or rubber band jumps") get their own pass — v0.18.18 task E.

### 1. Inline onSelect in App gives RevisionGrid a new clickRow/contextRow every App render, defeating memo(RevisionRow) for all ~60 visible rows

- Where: `frontend/src/App.tsx:365` — render-cascade, symptom: click-latency, impact claimed high, skeptic says medium
- Mechanism: HistoryPane gets `onSelect={(i) => setSelectedSha(rows[i]?.rev.id ?? null)}` — a new closure per App render. RevisionGrid derives `clickRow = useCallback(..., [onSelect, rows, onHighlightRoot])` (RevisionGrid.tsx:284-292) and `contextRow = useCallback(..., [onSelect])` (:293-299) and passes them to every RevisionRow (:429-430). RevisionRow is memo'd (RevisionRow.tsx:42) but its onClick/onContextMenu props change identity on every App render, so every row in the virtual window (≈36 visible + 24 overscan at ROW_HEIGHT=28) re-renders — each row also rebuilds RefChips (memo defeated by the inline `onExpand={() => onExpand(row.rev.id)}` and `onRefContextMenu` lambdas, RevisionRow.tsx:90-92) with its MUI SvgIcon glyphs. This happens on both click passes (finding 2), on every `refreshing` flip (finding 6), on every status/refs/stash update and on every splitter pointermove (finding 10). RevisionGrid already keeps the menu callbacks in refs (RevisionGrid.tsx:69-74) precisely to avoid this, but not onSelect.
- Evidence: App.tsx:365 `onSelect={(i) => setSelectedSha(rows[i]?.rev.id ?? null)}`; RevisionGrid.tsx:284-292 `const clickRow = useCallback((index, e) => { onSelect(index) ... }, [onSelect, rows, onHighlightRoot])`; RevisionRow.tsx:42 `export const RevisionRow = memo(...)`, :70 `onClick={(e) => onClick(index, e)}`; RevisionRow.tsx:90 `onExpand={() => onExpand(row.rev.id)}`.
- Skeptic: Confirmed: App.tsx:365 passes an inline `onSelect` lambda, HistoryPane.tsx:119 forwards it unchanged (HistoryPane is not memo'd), and RevisionGrid.tsx:284-299 puts `onSelect` in the deps of both `clickRow` and `contextRow`, which go to every RevisionRow at :429-430; RevisionRow.tsx:42 is memo'd so a new onClick identity defeats it for the whole virtual window (overscan 12, RevisionGrid.tsx:179). The trigger is real on hot interactions: a click calls `setSelectedSha` in App (App.tsx:67), and the splitter drag calls `setBottomHeight` on every pointermove (useChromeLayout.ts:50), so App re-renders and all ~50-60 visible rows re-render instead of the 2 whose `selected` flag changed. The RefChips half is also true (RevisionRow.tsx:90-92 inline lambdas), though the per-row cost is bounded: RefChips memoizes orderRefs/foldRefs (RefChips.tsx:55-60) and Glyph SvgIcons only exist on rows carrying refs, so a row re-render is mostly element creation + reconcile with no DOM writes.
- Fix: Simpler than proposed: only the App side is needed. Add `selectRow: (i: number) => setSelectedSha(rows[i]?.rev.id ?? null)` to the existing `chrome` useStable bag (App.tsx:146, useStable.ts is the latest-ref pattern and reads `rows` at call time, not render time) and pass `onSelect={chrome.selectRow}`. `onHighlightRoot={history.setHighlightRoot}` is already a stable setter and `rows` only changes on real data changes, so `clickRow`/`contextRow` become stable without touching RevisionGrid. The RefChips inline-lambda part becomes moot for unchanged rows once RevisionRow's memo holds; leave it unless a profiler shows RefChips renders on the two rows that legitimately re-render.
- Measurement: Extend frontend/src/components/RevisionGrid.test.ts (it already has "does not rescan unchanged rows when a parent rerender changes selection" at line 42): vi.mock RevisionRow's module or wrap it with a render counter, render RevisionGrid with 60 rows, rerender with a new `onSelect` lambda and a different `selected`, and assert the row render count is 2 not 60. Alternatively, in a dev build open React DevTools Profiler, enable "Highlight updates", click a row: every visible row flashes today; after the fix only two do. The end-to-end number is the click → Commit tab median in tests/perf/interaction.spec.ts:106, which will move by only a few ms since the diff fetch dominates.

### 2. Every in-app action triggers a second full refresh 1.2 s later: the SSE echo is deferred, never dropped

- Where: `frontend/src/hooks/useRepoState.ts:176` — engine-latency, symptom: periodic-stutter, impact claimed high, skeptic says medium

So a commit/checkout/reset does: engine call -> refresh #1 (git log -n3000 + for-each-ref + 4 status processes + stash list) -> 1.2 s later refresh #2 with the same scope. mergeReload usually reports `unchanged`, but the engine still spawns ~8 git processes and the client still downloads and JSON.parses the 3000-row page on the main thread, and setRefreshing(true/false) re-renders App twice. A commit-dialog stage (engine.stage, not under refresh, inFlight==0) also produces an SSE-driven `refresh({status:true})` 400 ms later: 4 more git processes for a status the POST already returned.
- Evidence: const echoDelay = Math.max(muteUntil.current - Date.now() + 100, inFlight.current > 0 ? ECHO_MS + 500 : 0)

- Skeptic: Confirmed in code: frontend/src/hooks/useRepoState.ts:166-188 only dedupes an identical payload and skips the initial snapshot; every other event arms a timer that unconditionally calls refresh(scope), and the comment at 171-175 says the echo is "deferred past the mute instead of dropped (v0.14.1)". GitHost.Watch.cs:76-89 bumps ChangeVersion on any HEAD/refs/index write regardless of writer and Program.cs:1211-1223 streams it every 500 ms, so every in-app commit/checkout/reset produces a second refresh 0.4-1.2 s later; the existing test useOperationActions.test.ts:234-256 pins it by asserting three page-0 fetches for one merge where the third "brings the same rows". The echo is not free: no server cache on /revisions, /refs, /status (Program.cs:211, 677, 689), the client re-parses a 3000-row page including commit bodies (types.ts:30), setRefs at useRepoState.ts:60 has no equality guard so App re-renders and RevisionGrid.tsx:61 rebuilds tagSet, re-rendering every visible RefChips, and StatusBar.tsx:104 flashes "refreshing…" a second time.

Impact is medium, not high: the echo lands 1.2 s after the action, reads bypass the write gate (Program.cs:180-183) so it never blocks the next mutation, and mergeReload skips setState on unchanged rows; the visible cost is a second "refreshing…" flash, ~8 git processes of engine CPU, and one JSON.parse of a multi-MB page that can be a single 20-50 ms long task on a big repository, felt only if the user is scrolling at that moment.
- Measurement: Run `npx vitest run src/hooks/useOperationActions.test.ts` from frontend/: the merge timeline test asserts `calls.toHaveLength(3)` at line ~250, and the third page-0 request is the echo (change `advance(1300)` to `advance(300)` and it drops to 2, proving the timer is the source). ### 3. Scroll: every visible-range change runs a flushSync React render inside the scroll handler and then rebuilds and redraws the entire graph canvas

- Where: `frontend/src/components/RevisionGrid.tsx:188` — grid-canvas, symptom: scroll-jank, impact claimed high, skeptic says medium
- Mechanism: @tanstack/react-virtual 3.14 notifies with `sync=true` while scrolling and calls `flushSync(rerender)` (node_modules/@tanstack/react-virtual/dist/esm/index.js:78-79); the range changes every 28 px of scroll, i.e. on most frames of a wheel or drag scroll. Each of those renders re-runs the whole RevisionGrid body (80 virtual items mapped, GraphOptionsBar re-rendered, see separate finding), `geometry` recomputes because `virtualItems` is a new array (lines 183-194), and since the render is on the SyncLane React flushes the passive canvas effect synchronously at the end of the commit: the canvas bitmap is reset (line 228-229), the whole 60-80 row band is re-stroked by drawRows and the canvas's `top` inline style moves (line 408), so the compositor gets a brand new 1-2 Mpx texture every frame. The browser's own style/layout/paint for the newly mounted rows comes on top of that, all inside one frame budget.
- Evidence: RevisionGrid.tsx:174-180 `useVirtualizer({ count: rows.length, getScrollElement: () => parentRef.current, estimateSize: () => ROW_HEIGHT, getItemKey, overscan: 12 })`; 183 `const virtualItems = virtualizer.getVirtualItems()`; 188-194 `const geometry = useMemo(() => {...gridGeometry(virtualItems, bandOf)}, [virtualItems, virtualizer])`; 405-410 `<canvas ... style={{ top: geometry.top, height: geometry.height, width }} />`; react-virtual index.js:78 `if (useFlushSync && sync) { flushSync(rerender); }`.
- Skeptic: The mechanism is confirmed, not refuted: virtual-core 3.17.8 calls `maybeNotify` from the native scroll listener with `isScrolling=true` and it is memoised on `[isScrolling, startIndex, endIndex]` (virtual-core index.js:350-372, 419-436), so every 28 px range change reaches react-virtual index.js:78 `flushSync(rerender)` (useFlushSync defaults true; RevisionGrid.tsx:174-180 passes no override). That SyncLane commit re-renders the grid body, `geometry` recomputes because `virtualItems` is a fresh array (RevisionGrid.tsx:183-194), and the passive effect at 223-238 is flushed synchronously, resetting the bitmap (228-229) and calling `drawRows` over ~56 bands (30 visible + 12+12 overscan + 2 neighbours, gridGeometry.ts:20-31). But "high" is overstated by the repo's own numbers: docs/perf/audit-2026-09-16.md:54-58,69 measured this exact 6 s wheel scroll at 10k rows (dev build) as 0 long tasks on two repos (21, max 77 ms on vscode), ~24-31 ms script per range-change render, with the profiler's top self time being React dev JSX and `graphWidth` (since memoised at RevisionGrid.tsx:137) and `drawRows` not in the top four; the hover path, which does the identical grid re-render + full-band redraw, is 32-34 ms dev (~8-12 ms prod, audit line 105) and was rated "fine". RevisionRow is `memo` (RevisionRow.tsx:42) with stable callbacks, so only 1-2 rows mount per step. The "1-2 Mpx texture" is the top end: the graph column is capped at 35% of the body (RevisionGrid.tsx:138-142), so a typical 150-300 px x 1568 px canvas is 0.25-0.5 Mpx at dpr 1.
- Fix: The proposed stationary-canvas + native rAF scroll listener rewrite is disproportionate. Two small changes get most of the win: (1) pass `useFlushSync: false` to `useVirtualizer` at RevisionGrid.tsx:174-180 so the scroll-driven rerender takes the continuous lane instead of SyncLane: React then batches several scroll events into one render and defers the passive canvas effect to after paint, so the redraw leaves the scroll handler and coalesces to at most once per frame; overscan 12 (336 px) covers the one-frame lag for wheel scrolling. (2) In the canvas effect (228-231) only assign `canvas.width`/`canvas.height` when the value actually changes (assigning the same value still discards the bitmap); `drawRows` already `clearRect`s (draw.ts:76), so this removes a realloc per step at zero risk. Also memoise `GraphOptionsBar` (RevisionGrid.tsx:451-456, separate finding) so it stops re-rendering per step. Only if a real WebView2 Performance trace still shows drawRows plus texture upload dominating scroll frames after that is the viewport-sized canvas worth doing.
- Measurement: Run `npm run test:perf -- -g "wheel scroll"` (frontend/tests/perf/interaction.spec.ts:140-154, instrumented by frontend/scripts/perf/metrics.mjs which counts a `.graph-canvas` clearRect as one redraw): the annotation's `redraws` equals the number of wheel steps (~74), proving one full-band redraw per range change, and `framesOver32`/`frameMaxMs` give the cost; change the loop to `page.mouse.wheel(0, 30)` every 16 ms to emulate smooth scrolling and re-run with and without `useFlushSync: false` to see the redraw count and frames-over-32 drop. Alternatively, in the app with Chrome DevTools Performance panel (WebView2 is Chromium), record a 3 s wheel scroll over the grid and look for the `scroll` event task containing `flushSync` > `commitRoot` > `drawRows` on every scroll event.

### 6. The 10 s status poll toggles `refreshing` true then false on every tick, forcing two App renders (and the full grid/compass cascade) even when status is unchanged

- Where: `frontend/src/hooks/useRepoState.ts:213` — grid-canvas, symptom: periodic-stutter, impact claimed medium, skeptic says low
- Mechanism: `refresh()` always calls `setRefreshing(true)` (line 48) and `setRefreshing(false)` in its finally (line 73). - Skeptic: The mechanism is real and fires on every reload that changes anything: useHistory.ts:139-143 only takes the append path when `revisions[0] === prev[0]` AND the list grew, but a reload puts new commits at index 0 (mergeReload, historyMerge.ts:68-76 builds `fresh` first), and a moved ref anywhere in page 0 keeps the length equal, so a reload can only ever produce `unchanged` (line 274) or a full `{reset: true, revisions}` post (line 150) — the "append" case the historyMerge.ts:5-11 comment describes never happens for a reload. I measured it with a throwaway vitest (deleted): a 10k synthetic layout (39k segments, 40-char ids) serialises to 11.8 MB, deserialises in ~73 ms on V8, layout takes ~88 ms in the worker, and the downstream markAncestry/graphNav index/scan add ~14 ms on the main thread, so the ~100 ms one-shot main-thread stall claim holds and scales linearly toward ~1 s if the user has scrolled to the 100k HARD_CEILING. The symptom label is wrong though: it is not periodic — status polls and focus refreshes that change nothing return `unchanged` and skip setState — it is one stall per real history change (commit, fetch that moved a page-0 ref, external write), landing asynchronously after the engine's ~300 ms reply, so it reads as a slightly delayed graph update rather than a stutter on the scroll/hover/select hot paths.
- Fix: The proposed "relayout from the first differing index" gains nothing for the common case, because the difference is at index 0 (a new commit lands on top) and lane assignment is top-down, so the worker would still relay out everything. Cheaper, simpler options: (1) keep the worker's previous rows and have it post back only rows whose lane/color/hasRefs/isHead/segments actually differ from last time (most rows below a new top commit are unchanged), with the main thread reusing the old GraphRow objects for the rest — this keeps row identity (RevisionRow memo hits, virtualizer keys) and cuts the reply to a few KB; (2) independently, drop the redundant strings from the transferred RowSegment (`id` is `${childId}:${parentId}` and can be derived on demand, and childId equals the row's own rev.id for most segments), which roughly halves the 11.8 MB payload. Either is a contained change in layout.worker.ts plus the `handle` callback at useHistory.ts:93-96.
- Measurement: Wrap the `handle` callback at frontend/src/hooks/useHistory.ts:93 in `console.time("layout-reply")`/`console.timeEnd` and, in Tauri devtools Performance panel, record a commit (or `git commit --allow-empty` from a terminal) on a 10k-commit repo with autofill complete: the reply shows as a single long "Message" task on the main thread (deserialise + setLiveGraphRows render) of ~100 ms, and no such task appears on a focus/poll refresh that changes nothing. Offline equivalent (under a minute): a vitest in src/graph that calls layoutGraph(syntheticHistory(10_000)) then node:v8 serialize/deserialize on the rows and prints byteLength and ms — I got 11.8 MB, 37 ms serialise, 73 ms deserialise, 88 ms layout.
